1. How to learn this permanently

Forgetting is normal: you lose most new information within a day or two unless you actively bring it back. Rereading this guide will feel productive but barely helps. These techniques actually work, ordered by impact.

The five techniques

  1. Retrieval practice. Close the guide and write or say everything you remember about a topic, then check what you missed. Recalling strengthens memory; rereading only creates familiarity.
  2. Spaced repetition. Review at growing intervals: 1 day, 3 days, 1 week, 2 weeks, 1 month. Use Anki (free) and write the cards yourself, in your own words, as questions.
  3. Build it. You remember what you did. Tie every concept to a moment in the project. You type the code; the mentor reviews it.
  4. Feynman technique. Explain a concept in plain language (Turkish or English) to a non-programmer. Where you stall or use jargon, you have a gap.
  5. Interleaving. Mix topics when practicing (one HTTP question, then a RAG one, then SQL). Interviews ask in random order.

A realistic routine

WhenWhatTime
DailyAnki reviews10-15 min
Each build sessionWrite one step yourself, get it reviewed, add 3-5 sentences to LEARNING_LOG.md45-90 min
End of each stepAnswer that topic's questions from chapter 15 out loud5 min
WeeklyDraw the whole system from memory and explain it15 min

Good flashcard example. Front: "401 vs 403?" Back: "401 = not authenticated (who are you?). 403 = authenticated but not allowed." Small, one idea, phrased as a question.

2. The big picture

Training a model vs providing context with RAG CORE

Training / fine-tuningRAG (Retrieval-Augmented Generation)
What changesThe model's weightsNothing in the model; the prompt gets extra context at request time
Good forBehavior, style, format, domain jargonFacts, changing data, per-user data, citations
Updating knowledgeRetrain (hours, money)Re-index a document (seconds)
AuditabilityHard: "where did it learn that?"Easy: you can show the retrieved sources
AnalogyMemorizing the textbookOpen-book exam

Why RAG fits a fitness coach: biometrics change daily, advice must be grounded in vetted protocols (safety), knowledge updates should be cheap, and you cannot fine-tune a model per user per day. Fine-tuning may later adjust tone, never facts.

Also know: the cheapest option is plain prompting. The usual decision order is: prompt engineering, then RAG, then fine-tuning, then training from scratch (almost never).

Two kinds of context CORE

  • Structured (HRV, sleep score, calories, weight): lives in SQL, fetched with an exact query ("user u1, last 7 days").
  • Unstructured (recovery protocols, nutrition guidelines): lives in a vector DB, fetched by semantic similarity ("things related to CNS fatigue").

Putting numeric user data into a vector DB is a classic junior mistake: similarity search is fuzzy, and you need exact numbers.

The request flow

User question ──► embed question ──► vector search (Qdrant) ──► top-k protocol chunks ─┐ ├─► build prompt ──► LLM ──► answer + sources user_id ─────────► exact lookup (JSON now, Postgres later) ──► recent biometrics ─────┘ Offline (ingestion): protocols.json ──► chunk ──► embed ──► upsert into Qdrant with metadata

3. HTTP fundamentals

Every REST API is HTTP underneath. Understand HTTP and every framework becomes easy.

Anatomy of a request

POST /api/v1/ask HTTP/1.1                       <- method, path, version
Host: api.fitcoach.com                          <- headers (metadata)
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{"user_id": "u1", "question": "My HRV dropped, adjust leg day?"}   <- body

The response has the same shape: a status line (HTTP/1.1 200 OK), headers, and a body.

Methods, safety and idempotency CORE

MethodPurposeSafe?Idempotent?
GETReadYesYes
POSTCreate or trigger an actionNoNo
PUTReplace the whole resourceNoYes
PATCHPartial updateNoNot guaranteed
DELETERemoveNoYes
  • Safe: does not change server state.
  • Idempotent: doing it once or ten times has the same effect. Networks fail and clients retry, so idempotent operations are safe to retry. POST /payments twice charges twice; that is why idempotency keys exist (chapter 7).

Status codes CORE

CodeMeaningTypical use
200OKSuccessful read or update
201CreatedPOST created a resource
202AcceptedWork queued, finishes later (long AI jobs)
204No ContentSuccessful DELETE
400Bad RequestMalformed request
401UnauthorizedNot authenticated: missing or invalid token
403ForbiddenAuthenticated, but not allowed
404Not FoundResource does not exist
409ConflictDuplicate or state conflict
422Unprocessable EntityValidation failed (FastAPI default)
429Too Many RequestsRate limit hit
500Internal Server ErrorYour bug
502 / 503 / 504Bad Gateway / Unavailable / Gateway TimeoutAn upstream service failed or is overloaded

Rule of thumb: 4xx = client's fault, 5xx = server's fault. Only 429 and 5xx are generally worth retrying.

Headers worth knowing

  • Content-Type: format of the body I am sending (application/json).
  • Accept: format I want back.
  • Authorization: credentials, usually Bearer <token>.
  • Retry-After: how long to wait before retrying (with 429 or 503).
  • Cache-Control, ETag: caching rules and resource versions.
  • X-Request-ID: correlation ID to trace one request through all logs.

Statelessness and HTTPS

Stateless: each request carries everything the server needs (including auth). The server keeps no memory of the client between requests, so any of N identical servers can handle any request. This is what makes horizontal scaling easy.

HTTPS = HTTP over TLS: encrypts traffic and proves the server's identity. Always required in production, especially for health data.

4. REST API design

REST models your system as resources (nouns) acted on by HTTP methods (verbs).

URL design CORE

Good                                    Bad
GET    /users/u1                        GET  /getUser?id=u1
GET    /users/u1/biometrics?days=7      POST /fetchBiometricsForUser
POST   /users/u1/workouts               POST /createWorkout
PATCH  /users/u1/workouts/42            POST /updateWorkout
DELETE /users/u1/workouts/42            GET  /deleteWorkout?id=42
  • Plural nouns, no verbs in paths. Nesting expresses ownership.
  • Query parameters for filtering, sorting and pagination: ?days=7&sort=-recorded_on.
  • Pragmatic exception: non-CRUD actions are fine as POST, e.g. POST /ask or POST /plans:generate. Be consistent.

Versioning

Prefix with /api/v1. Once customers integrate you cannot break them. Additive changes (a new optional field) are fine in v1; breaking changes (renaming or removing a field, changing a type) go in v2.

Pagination

StyleExamplePros / cons
Offset?limit=50&offset=100Simple; slow on big tables; items shift if data changes while paging
Cursor?limit=50&cursor=abc123, response has next_cursorStable and fast; cannot jump to page 37. Google APIs use this (pageToken)

Never return unbounded lists.

Consistent error format

{"error": {"code": "user_not_found", "message": "User u9 does not exist", "request_id": "req_8f2a"}}

A machine-readable code, a human-readable message, and a request_id for support.

REST vs alternatives

StyleUse it when
RESTDefault for public and customer-facing APIs; simple, cacheable, universal
GraphQLComplex frontends that need flexible field selection; harder to cache and secure
gRPCInternal service-to-service calls; binary, fast, strict protobuf schemas
WebSocketsTwo-way real-time communication (live chat, multiplayer)
SSE (Server-Sent Events)One-way server-to-client streaming; how LLM token streaming usually works

5. FastAPI

The stack

  • FastAPI: the framework; maps paths to Python functions.
  • Uvicorn: the server; handles networking and calls FastAPI.
  • ASGI: the async interface between them (successor of WSGI used by Flask/Django).
  • Pydantic: data validation from type hints.

Run with uvicorn app.main:app --reload ("in app/main.py, serve the object app; restart on file changes"). Interactive docs at /docs are generated from your type hints (OpenAPI / Swagger).

Why FastAPI over Flask? Type-driven validation, automatic docs, native async, high performance; the de-facto choice for ML serving.

Where inputs come from CORE

from fastapi import FastAPI, Query

app = FastAPI()

@app.get("/users/{user_id}/biometrics")
def list_biometrics(
    user_id: str,                           # in the path -> path parameter
    days: int = 7,                          # simple type -> query: ?days=14
    limit: int = Query(50, ge=1, le=200),   # query with validation
): ...

@app.post("/users/{user_id}/workouts", status_code=201)
def create_workout(user_id: str, workout: WorkoutCreate): ...   # Pydantic model -> JSON body

Pydantic and "validate at the boundary" CORE

from pydantic import BaseModel, Field

class AskRequest(BaseModel):
    user_id: str
    question: str = Field(..., min_length=3, max_length=2000)   # ... = required

FastAPI parses the JSON, validates it, and either gives you a typed object or returns 422 with a precise error before your code runs. Bad data is stopped at the door, so the rest of the system can trust its inputs.

str | None = None means the field is optional and defaults to None.

Separate input and output models

class WorkoutCreate(BaseModel):     # what the client sends
    name: str
    sets: int = Field(gt=0, le=20)

class WorkoutRead(WorkoutCreate):   # what the API returns
    id: int
    created_at: datetime

@app.post("/workouts", response_model=WorkoutRead, status_code=201)
def create(w: WorkoutCreate): ...

Clients must not set id; you must never return password_hash. response_model enforces the output contract and filters extra fields.

Errors

from fastapi import HTTPException

if user is None:
    raise HTTPException(status_code=404, detail=f"User {user_id} not found")

Dependency injection with Depends CORE

from fastapi import Depends, Header, HTTPException

def get_current_user(authorization: str = Header(...)) -> User:
    user = verify_token(authorization.removeprefix("Bearer "))
    if user is None:
        raise HTTPException(status_code=401, detail="Invalid token")
    return user

@app.get("/me/biometrics")
def my_biometrics(user: User = Depends(get_current_user)):
    return load_biometrics(user.id)

A dependency runs before the handler and injects its result. Use it for DB sessions, the current user, settings and clients. Two big wins:

  1. No duplicated logic (auth, DB setup) across endpoints.
  2. Testability: app.dependency_overrides[get_llm] = lambda: FakeLLM() lets you test without calling OpenAI.

Project structure: routers and layers

# app/routers/workouts.py
router = APIRouter(prefix="/api/v1/workouts", tags=["workouts"])

# app/main.py
app.include_router(workouts.router)
Router (HTTP only) ──► Service (business logic) ──► Data access (DB, Qdrant, external APIs)

Routers parse requests and shape responses; services decide what to do; the data layer talks to storage. Logic becomes reusable from scripts and jobs, and each layer is testable alone.

Lifespan: create expensive things once

from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.qdrant = QdrantClient(path="./qdrant_data")   # startup
    yield
    app.state.qdrant.close()                                 # shutdown

app = FastAPI(lifespan=lifespan)

Middleware and CORS

Middleware wraps every request: logging, request IDs, timing, CORS. CORS is the browser rule that blocks a page on app.com from calling api.com unless the API allows that origin. "Works in Postman, fails in the browser" almost always means CORS. It is a browser protection, not a server security feature.

Sync vs async CORE

  • def handlers run in a thread pool: blocking code is acceptable.
  • async def handlers run on the event loop: everything inside must be non-blocking (await httpx.AsyncClient().get(...), AsyncOpenAI).
  • A blocking call (time.sleep, requests.get, sync DB driver) inside async def freezes all concurrent requests. Most common FastAPI bug.
  • LLM apps are I/O-bound (waiting on OpenAI, DBs), which is exactly where async shines. CPU-bound work (embedding locally, heavy NumPy) belongs in worker processes.

Streaming LLM output

from fastapi.responses import StreamingResponse

@app.post("/ask/stream")
def ask_stream(payload: AskRequest):
    def tokens():
        stream = client.chat.completions.create(
            model="gpt-4o-mini", messages=build_messages(payload), stream=True
        )
        for chunk in stream:
            yield chunk.choices[0].delta.content or ""
    return StreamingResponse(tokens(), media_type="text/plain")

Users see text after a few hundred milliseconds instead of waiting for the full answer. Key metric: time to first token (TTFT).

Long-running jobs

POST /ingest-jobs       -> 202 Accepted  {"job_id": "j1"}
GET  /ingest-jobs/j1    -> {"status": "running", "progress": 0.4}

Don't hold an HTTP request open for minutes. Queue the work (Celery, RQ, Arq; or BackgroundTasks for small jobs) and let the client poll or receive a webhook.

6. Authentication, authorization and security

Authn vs authz CORE

  • Authentication: who are you? Failure = 401.
  • Authorization: what may you do? Failure = 403.

Mechanisms

MechanismHow it worksTypical use
API keyStatic secret in a headerServer-to-server (your OpenAI key)
Session cookieServer stores session, browser sends cookieTraditional web apps
JWTSigned token with claims (sub, exp); verified without a DB lookupMobile and SPA backends, microservices
OAuth2Delegated access: "app X may read my data at service Y"Google Health, FatSecret, "Login with Google"

A JWT is signed, not encrypted. Anyone can base64-decode and read it. Never put secrets in it. Keep expiry short.

OAuth2 Authorization Code flow (+ PKCE) CORE

  1. Your app redirects the user to Google with client_id, requested scopes, redirect_uri, a state value (CSRF protection) and a PKCE challenge.
  2. The user logs in at Google and consents.
  3. Google redirects back to your redirect_uri with a short-lived code.
  4. Your backend exchanges the code (plus client secret / PKCE verifier) for an access token (short-lived, ~1 hour) and a refresh token (long-lived).
  5. Call the API with Authorization: Bearer <access_token>. When it expires, use the refresh token to get a new one.

Forgetting step 5's refresh logic is the top reason integrations "randomly break after an hour". Client Credentials flow is the machine-to-machine variant with no user. Scopes limit what a token may do: request the minimum.

BOLA: the #1 API vulnerability CORE

@app.get("/users/{user_id}/biometrics")
def get_bio(user_id: str, user: User = Depends(get_current_user)):
    if user.id != user_id:
        raise HTTPException(status_code=403)   # without this, any logged-in user
    ...                                        # can read anyone's health data

Broken Object Level Authorization tops the OWASP API Security Top 10. Being logged in is not the same as being allowed. Check ownership on every object access.

Security checklist

  • HTTPS everywhere; validate all input (Pydantic); parameterized SQL (never string-format queries).
  • Never log secrets, tokens or health data; least-privilege keys and scopes.
  • Rate-limit per user/key; hash passwords with bcrypt or argon2 (never store plain text).
  • Health data is sensitive personal data under GDPR (special category). Know: consent, data minimization, right to deletion, encryption at rest.
  • For LLM apps, also prompt injection (chapter 12).

7. Consuming external APIs

As an FDE you will spend more time calling other people's APIs (customer systems, Google, FatSecret, OpenAI) than building your own. Robust clients assume failure.

The checklist for every external call CORE

  1. Timeouts always. No timeout means one hung upstream can hang your service.
  2. Retry only retryable errors: 429, 5xx, network errors. Never retry 400/401/403/404/422.
  3. Exponential backoff with jitter: ~1s, 2s, 4s, 8s plus randomness, so thousands of clients do not retry in sync (thundering herd).
  4. Respect Retry-After when given.
  5. Idempotency keys for non-idempotent writes: Idempotency-Key: <uuid> lets the server drop duplicates.
  6. Circuit breaker: after repeated failures, stop calling for a while and fail fast or degrade gracefully.
import random
import time

import httpx

RETRYABLE = {429, 500, 502, 503, 504}

def get_json_with_retry(url: str, headers: dict, max_attempts: int = 5) -> dict:
    for attempt in range(max_attempts):
        try:
            r = httpx.get(url, headers=headers, timeout=10.0)
            if r.status_code not in RETRYABLE:
                r.raise_for_status()           # 4xx: fail fast, no retry
                return r.json()
            retry_after = r.headers.get("Retry-After", "")
        except httpx.TransportError:           # DNS, connection reset, timeout
            retry_after = ""
        delay = float(retry_after) if retry_after.isdigit() else min(2**attempt, 30) + random.random()
        time.sleep(delay)
    raise RuntimeError(f"Gave up on {url} after {max_attempts} attempts")

In real code, the tenacity library does this declaratively. Be able to write it by hand in an interview.

Webhooks

The other service calls you when something happens ("new sleep data").

import hashlib
import hmac

expected = hmac.new(WEBHOOK_SECRET, raw_body, hashlib.sha256).hexdigest()
if not hmac.compare_digest(expected, request.headers["X-Signature"]):
    raise HTTPException(status_code=401)
  • Verify the signature over the raw body, or anyone can send you fake events. compare_digest prevents timing attacks.
  • Respond 2xx quickly; do heavy work in the background, or the sender times out and retries.
  • Expect duplicates and out-of-order delivery: deduplicate on event ID.

Polling vs webhooks

Polling is simple but wasteful and laggy; webhooks are real-time but more complex. Robust integrations use webhooks plus a periodic reconciliation sync to catch missed events.

Reading unfamiliar API docs: the five questions

  1. How do I authenticate (API key, OAuth2 which flow, scopes)?
  2. What are the rate limits and how are they signaled?
  3. How does pagination work?
  4. What does an error look like?
  5. What are the data units and time zones (HRV in ms? timestamps UTC or local?)

Data normalization matters: map every provider into your schema (an adapter per provider), so the rest of the system never depends on Google's or FatSecret's format.

async in one picture

import asyncio
import httpx

async def fetch_all(urls: list[str]) -> list[int]:
    async with httpx.AsyncClient(timeout=10) as client:
        responses = await asyncio.gather(*(client.get(u) for u in urls))
    return [r.status_code for r in responses]

Ten 1-second requests take about 1 second total instead of 10, because the event loop switches tasks while each one waits on the network. Async does not make CPU work faster.

Concurrency vocabulary

  • I/O-bound (network, disk): use async or threads.
  • CPU-bound (math, local models): use multiple processes; the GIL limits threads for CPU work in standard CPython.

9. SQL and relational databases

Core concepts CORE

  • Table = rows (records) and columns (typed fields).
  • Primary key (PK): unique identifier of a row (users.id).
  • Foreign key (FK): column referencing another table's PK (daily_biometrics.user_id -> users.id); the DB enforces the relationship.
  • Constraints: NOT NULL, UNIQUE (user_id, recorded_on) (one row per user per day; enables idempotent upserts), CHECK (sleep_score BETWEEN 0 AND 100).
  • Index: a data structure (usually a B-tree) that makes lookups fast, like a book index. Speeds reads, slows writes slightly. Index columns you filter or join on.

Our schema

CREATE TABLE users (
    id          UUID PRIMARY KEY,
    email       TEXT UNIQUE NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE daily_biometrics (
    id            UUID PRIMARY KEY,
    user_id       UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    recorded_on   DATE NOT NULL,
    hrv_ms        REAL,
    sleep_score   INT CHECK (sleep_score BETWEEN 0 AND 100),
    resting_hr    INT,
    calories_kcal INT,
    UNIQUE (user_id, recorded_on)
);
CREATE INDEX ix_bio_user_date ON daily_biometrics (user_id, recorded_on);

Queries you must be able to write CORE

-- Filter, sort, limit
SELECT recorded_on, hrv_ms FROM daily_biometrics
WHERE user_id = :uid ORDER BY recorded_on DESC LIMIT 7;

-- JOIN
SELECT u.email, b.recorded_on, b.hrv_ms
FROM users u
JOIN daily_biometrics b ON b.user_id = u.id
WHERE b.recorded_on >= CURRENT_DATE - INTERVAL '7 days';

-- Aggregate with GROUP BY / HAVING
SELECT user_id, AVG(sleep_score) AS avg_sleep
FROM daily_biometrics GROUP BY user_id HAVING AVG(sleep_score) < 60;

-- Window function: 7-day rolling HRV baseline
SELECT recorded_on, hrv_ms,
       AVG(hrv_ms) OVER (ORDER BY recorded_on
                         ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS hrv_7d_avg
FROM daily_biometrics WHERE user_id = :uid;

-- Upsert (idempotent ingestion from Google Health)
INSERT INTO daily_biometrics (id, user_id, recorded_on, hrv_ms)
VALUES (:id, :uid, :day, :hrv)
ON CONFLICT (user_id, recorded_on) DO UPDATE SET hrv_ms = EXCLUDED.hrv_ms;

Know the JOIN types: INNER (only matches), LEFT (all left rows, NULLs when no match). WHERE filters rows before grouping; HAVING filters groups after.

Transactions and ACID

  • Atomicity: all statements succeed or none do.
  • Consistency: constraints always hold.
  • Isolation: concurrent transactions don't see each other's half-done work.
  • Durability: committed data survives crashes.

Design and performance

  • Normalization: store each fact once (user email only in users). Denormalize deliberately for read speed.
  • N+1 problem: 1 query for 100 users, then 100 queries for their biometrics. Fix with a JOIN or eager loading.
  • SQL injection: never build SQL with f-strings from user input. Use parameters (:uid) or the ORM.
  • EXPLAIN ANALYZE shows how Postgres executes a query (index scan vs sequential scan).
  • Connection pooling: reuse DB connections instead of opening one per request.

ORM and migrations

class DailyBiometrics(Base):
    __tablename__ = "daily_biometrics"
    id: Mapped[UUID] = mapped_column(primary_key=True, default=uuid4)
    user_id: Mapped[UUID] = mapped_column(ForeignKey("users.id"), index=True)
    hrv_ms: Mapped[float | None]

stmt = select(DailyBiometrics).where(DailyBiometrics.user_id == uid).limit(7)
rows = session.scalars(stmt).all()

SQLAlchemy maps Python classes to tables. Alembic manages migrations: versioned scripts that evolve the schema (add a column) safely in every environment. Never edit production schemas by hand.

10. Embeddings and vector databases

What an embedding is CORE

An embedding model turns text into a list of numbers (a vector) such that texts with similar meaning end up close together in that space. text-embedding-3-small produces 1536 numbers per text. "CNS fatigue after heavy squats" and "nervous system feels fried" land near each other even with no shared words. That is the advantage over keyword search.

from openai import OpenAI

client = OpenAI()
resp = client.embeddings.create(model="text-embedding-3-small",
                                input=["HRV dropped 15% today", "Zone 2 cardio for recovery"])
vectors = [d.embedding for d in resp.data]     # two lists of 1536 floats

Rule: the query and the documents must be embedded with the same model. Changing models means re-embedding everything.

Similarity metrics CORE

Cosine similarity = cos(angle between vectors) = (a · b) / (|a| |b|). Range -1 to 1; higher = more similar. It ignores vector length and compares direction only.

import numpy as np

def cosine(a: np.ndarray, b: np.ndarray) -> float:
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))
  • Dot product: equals cosine when vectors are normalized to length 1 (OpenAI embeddings are), and is cheaper to compute.
  • Euclidean distance: straight-line distance; lower = more similar.

Why a vector database? CORE

Brute force compares the query with every vector: cost grows with N x dimensions. Fine for 1,000 documents, too slow for 10 million. Vector DBs use Approximate Nearest Neighbor (ANN) indexes, which trade a little accuracy for huge speed.

  • HNSW (Hierarchical Navigable Small World): a layered graph; search starts at a sparse top layer and greedily descends to dense lower layers. Roughly logarithmic search time. Parameters (m, ef) trade recall vs speed and memory. Used by Qdrant, pgvector, Weaviate.
  • IVF: cluster vectors and search only nearby clusters. PQ (product quantization): compress vectors to save memory.
  • Beyond the index, a vector DB also gives you persistence, metadata (payload) filtering, updates and deletes, replication and an API.

Choosing a vector store

OptionProsCons
Qdrant (our choice)Open source, runs embedded in Python or as a server, strong payload filtering, fast (Rust)One more system to operate in production
PineconeFully managed, zero opsPaid, cloud-only, vendor lock-in, cannot run locally
pgvectorLives inside Postgres: one database, SQL joins with user data, transactionsLess specialized at very large scale

Qdrant basics

from qdrant_client import QdrantClient
from qdrant_client.models import Distance, FieldCondition, Filter, MatchValue, PointStruct, VectorParams

client = QdrantClient(path="./qdrant_data")           # embedded mode, no Docker
client.create_collection("protocols",
    vectors_config=VectorParams(size=1536, distance=Distance.COSINE))

client.upsert("protocols", points=[
    PointStruct(id=1, vector=vec, payload={"title": "HRV autoregulation", "category": "recovery"}),
])

hits = client.query_points("protocols", query=query_vec, limit=3,
    query_filter=Filter(must=[FieldCondition(key="category", match=MatchValue(value="recovery"))]),
).points
for h in hits:
    print(h.score, h.payload["title"])

Vocabulary: collection (like a table), point (id + vector + payload), payload (metadata JSON you can filter on).

11. The RAG pipeline and evaluation

Two pipelines CORE

Ingestion (offline): load documents, clean them, split into chunks, embed each chunk, upsert into the vector DB with metadata (source, title, category, date).

Query (online): embed the question, retrieve top-k chunks (with filters), optionally rerank, build a prompt (instructions + user data + chunks + question), generate, return the answer with cited sources.

Chunking

  • Why: embedding a whole 30-page document blurs its meaning into one vector, and you cannot fit everything in the prompt.
  • Strategies: fixed size (e.g. ~300-800 tokens) with overlap (10-20%) so ideas are not cut in half; recursive splitting on paragraphs and sentences; semantic or structure-aware splitting (headings, sections).
  • Trade-off: small chunks are precise but lose context; large chunks keep context but dilute relevance and cost more tokens.
  • Store parent document ID in metadata so you can fetch neighbors or cite the source.

Improving retrieval

TechniqueWhat it does
Metadata filteringRestrict search (category = nutrition, language = tr, user's injuries)
Hybrid searchCombine dense vectors (meaning) with BM25 keyword search (exact terms like "RPE", drug names). Merge with Reciprocal Rank Fusion
RerankingRetrieve ~20-50 candidates fast, then rescore with a cross-encoder that reads query and chunk together; keep the best 3-5. More accurate, slower
Query rewritingLLM turns a vague or conversational question into a better search query (or several)
Contextual retrievalEnrich the query with structured context ("HRV -15% vs baseline") before embedding

Failure modes CORE

  • Retrieval miss: the right chunk was not retrieved, so the LLM answers from its own memory (hallucination risk).
  • Irrelevant context: wrong chunks distract or mislead the model.
  • Lost in the middle: models use information at the start and end of long contexts better than the middle. More chunks is not always better.
  • Stale index: documents changed but embeddings were not updated.
  • Unfaithful answer: correct chunks retrieved, but the answer contradicts or goes beyond them.

Mitigations: instruct the model to answer only from context and say "I don't know" otherwise, require citations by chunk ID, set a similarity score threshold, and evaluate.

Evaluation: "how do you know it works?" CORE

Build a golden set: 30-100 realistic questions, each labeled with the chunk(s) that should be retrieved and key facts the answer must contain. Evaluate the two halves separately.

StageMetricMeaning
RetrievalRecall@k (hit rate)Share of questions where a correct chunk appears in the top k
RetrievalMRRMean of 1 / rank of the first correct chunk (rewards ranking it first)
RetrievalPrecision@kShare of the top k that is relevant
GenerationFaithfulness / groundednessIs every claim supported by the retrieved context?
GenerationAnswer relevance / correctnessDoes it answer the question; does it contain the key facts?

LLM-as-judge: a strong model grades answers against a rubric. Cheap and scalable, but validate it against human labels on a sample. Tools: Ragas, DeepEval, promptfoo. Run the eval on every change (chunk size, model, prompt) so improvements are measured, not guessed.

12. LLMs and LLM APIs

Core vocabulary CORE

  • Token: the unit models read and bill by; roughly 4 characters or 0.75 English words. Turkish usually needs more tokens per word.
  • Context window: max tokens of input + output per call. Bigger is not free: cost, latency and "lost in the middle".
  • Temperature: randomness. Low (0-0.3) for factual, consistent answers; higher for creative text.
  • Roles: system (rules and persona), user (input), assistant (model output). The API is stateless: you resend the conversation history every call.
  • Hallucination: fluent but false output. RAG, citations and evaluation reduce it; nothing removes it fully.

A chat completion

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    temperature=0.2,
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": f"Biometrics:\n{bio}\n\nProtocols:\n{chunks}\n\nQuestion: {q}"},
    ],
)
answer = resp.choices[0].message.content
usage = resp.usage            # prompt_tokens, completion_tokens: log these for cost tracking

Prompt structure for RAG

  1. Role and goal ("You are an evidence-informed strength and recovery coach").
  2. Rules: use only the provided context; cite protocol IDs; say when information is missing; no medical diagnosis; recommend a professional for red flags.
  3. Clearly delimited data sections (user biometrics, retrieved protocols with IDs).
  4. The question and the desired output format.

Structured outputs and tool calling

  • Structured outputs: force the model to return JSON matching a schema (e.g. a Pydantic WorkoutPlan), then validate it. Turns text into data your backend can use.
  • Tool / function calling: you describe functions (get_biometrics(days), search_protocols(query)); the model replies with which function to call and arguments; your code executes it and sends the result back. This loop is the basis of "agents". The model never executes anything itself.

Cost, latency and reliability

  • Cost = input tokens x price + output tokens x price. Output tokens are typically several times more expensive. Fewer, better chunks save money.
  • Latency: use smaller models where possible, stream output, cache repeated work, run independent calls in parallel.
  • Provider errors happen (429, 5xx, timeouts): apply chapter 7. Consider a fallback model.

Prompt injection and guardrails CORE

Untrusted text (user input, retrieved documents, web pages, API data) can contain instructions like "ignore previous instructions". Mitigations:

  • Treat retrieved content as data: delimit it and tell the model it is reference material, not instructions.
  • Least privilege for tools: the model should not be able to delete data or access other users' records.
  • Validate outputs (schemas, allow-lists), and enforce authorization in code, never in the prompt.
  • Domain guardrails: detect medical red flags (chest pain, fainting) and respond with a safe, fixed message.

When to use what

NeedApproach
Better format or instructionsPrompt engineering, few-shot examples
Knowledge that changes or is privateRAG
Consistent style or narrow task at lower costFine-tuning (often a small model)
Taking actions, multi-step workTool calling / agents

13. System design for AI applications

Interview framework CORE

  1. Clarify requirements: functional (what it does) and non-functional (latency, scale, availability, privacy, cost).
  2. Estimate: users, requests per second, data size, token cost per request.
  3. API: the main endpoints and their inputs and outputs.
  4. Data model: what lives in SQL, vector DB, cache, object storage.
  5. High-level architecture: draw boxes and arrows.
  6. Deep dive: the hardest part (retrieval quality, ingestion at scale, sync with external APIs).
  7. Trade-offs and failure modes: what breaks first, how you monitor and evolve it.

Always say the trade-off out loud: "I chose X over Y because..., at the cost of...".

Reference architecture for our coach

Mobile app ──► API gateway / load balancer ──► FastAPI (stateless, N replicas) │ │ │ ▼ ▼ ▼ Postgres Qdrant Redis (cache, rate limits) ▲ │ │ ▼ Google Health / FatSecret ──► webhooks + scheduled sync ──► queue ──► workers (normalize, upsert) FastAPI ──► LLM provider (OpenAI) Observability: logs, metrics, traces, eval dashboard

Key building blocks

  • Stateless API + load balancer: scale horizontally by adding replicas.
  • Queue + workers (Redis/RQ, Celery, SQS): decouple slow or bursty work (ingestion, nightly plan generation) from user requests; retries and backpressure.
  • Caching: embedding cache (same text, same vector), response cache for repeated questions, cache-aside pattern; always define invalidation.
  • Rate limiting: token bucket per user; protects you from abuse and runaway LLM bills.
  • Observability: structured logs with request IDs; metrics (p50/p95/p99 latency, error rate, tokens and cost per request); tracing (OpenTelemetry, Langfuse) showing time per step: "2.1s in LLM, 40ms in Qdrant".
  • Reliability: timeouts, retries, circuit breakers, graceful degradation (if the LLM is down, return a rule-based recommendation).
  • Privacy: encrypt at rest and in transit, minimize data sent to the LLM, per-user isolation, audit logs, deletion on request.

15. Interview question bank

Answer out loud before reading the answer. If you can't, mark it for review.

HTTP and REST

PUT vs PATCH?
PUT replaces the whole resource and is idempotent; PATCH updates part of it.
401 vs 403?
401: not authenticated. 403: authenticated but not permitted.
What is idempotency and why does it matter?
Repeating a request has the same effect as doing it once. It makes retries safe on unreliable networks. For POST, use idempotency keys.
Which errors should a client retry?
429, 5xx and network errors, with exponential backoff and jitter, respecting Retry-After. Never 4xx validation or auth errors.
Offset vs cursor pagination?
Offset is simple but slow and unstable on large or changing data; cursor is stable and fast.
What does "stateless" mean and why care?
Each request contains everything needed; servers keep no client session state, so you can scale horizontally behind a load balancer.
How do you version an API?
URL prefix (/v1) or header; additive changes stay in the same version, breaking changes get a new version with a deprecation period.

FastAPI and Python

Why FastAPI?
Pydantic validation, auto OpenAPI docs, async support, performance; standard for ML serving.
What happens when the request body is invalid?
Pydantic validation fails and FastAPI returns 422 with details before the handler runs.
What is dependency injection in FastAPI and why use it?
Depends() runs provider functions (DB session, current user, clients) and injects results. Removes duplication and allows overriding dependencies in tests.
def vs async def?
def runs in a thread pool; async def runs on the event loop and must not block. Blocking inside async def stalls all requests.
How do you test an endpoint that calls OpenAI?
TestClient plus dependency_overrides to replace the LLM client with a fake returning fixed output.
How do you serve a slow LLM response well?
Stream tokens (SSE / StreamingResponse) for chat; for batch work return 202 with a job ID and process in a worker.

Security

Explain the OAuth2 Authorization Code flow.
Redirect to provider with scopes and state, user consents, provider redirects back with a code, backend exchanges code for access + refresh tokens, refresh when the access token expires. PKCE protects the code exchange.
What is BOLA?
Broken Object Level Authorization: users can access other users' objects by changing an ID. Prevent by checking ownership on every access.
Is a JWT encrypted?
No, it is signed. Anyone can read its payload; the signature only proves it wasn't tampered with.
How do you verify a webhook?
Compute an HMAC of the raw body with the shared secret and compare with compare_digest; respond fast and deduplicate by event ID.

SQL

What is an index and what does it cost?
A structure (usually B-tree) for fast lookups on a column; speeds reads, costs storage and slightly slower writes.
WHERE vs HAVING?
WHERE filters rows before grouping; HAVING filters groups after aggregation.
What is the N+1 problem?
One query for a list, then one query per item. Fix with JOINs or eager loading.
Explain ACID.
Atomicity, Consistency, Isolation, Durability: transactions are all-or-nothing, keep constraints valid, don't interfere, and persist after commit.
How do you make ingestion idempotent?
A unique constraint on the natural key (user_id, date) plus INSERT ... ON CONFLICT DO UPDATE.

Vectors and RAG

Training vs RAG?
Training changes weights (behavior, style); RAG injects retrieved context at request time (facts, fresh and private data, citations). RAG is cheaper to update and auditable.
What is an embedding?
A vector representation of text where semantic similarity becomes geometric closeness.
Cosine similarity vs dot product?
Cosine compares direction only; for normalized vectors they are identical and dot product is cheaper.
Why not just brute-force search?
Cost grows linearly with N; ANN indexes like HNSW give near-logarithmic search with a small recall trade-off.
Qdrant vs Pinecone vs pgvector?
Qdrant: open source, local or server, strong filtering. Pinecone: managed, lock-in, paid. pgvector: one DB with SQL joins, less specialized at large scale.
How do you choose chunk size?
Start with a few hundred tokens with overlap, then measure recall on a golden set; small = precise but less context, large = more context but diluted.
How do you evaluate a RAG system?
Golden set; retrieval metrics (recall@k, MRR) and generation metrics (faithfulness, relevance) via human or LLM-as-judge; run on every change.
Retrieval returns nothing relevant. What should happen?
Score threshold; the model says it lacks information instead of guessing; log the query to improve the knowledge base.
What is hybrid search?
Combining dense vector search with keyword search (BM25) and fusing results; helps with exact terms and rare words.
What is reranking?
Retrieve many candidates cheaply, then rescore with a cross-encoder that reads query and chunk together; better precision at extra latency.

LLMs and system design

What is prompt injection and how do you mitigate it?
Untrusted text containing instructions. Delimit data, least-privilege tools, validate outputs, enforce authorization in code.
How does tool calling work?
The model outputs a function name and arguments; your code executes it and returns the result to the model, looping until done.
How would you reduce LLM cost?
Smaller models for easy tasks, fewer/better chunks, caching, shorter prompts, batching, limiting output length, tracking tokens per request.
What breaks first at 100x users?
LLM rate limits and cost, then DB connections and sync jobs. Answer with: queues, caching, rate limits, replicas, connection pooling, monitoring.
How would you design ingestion from Google Health for 1M users?
OAuth tokens stored encrypted; webhooks plus scheduled sync; a queue with workers; per-user rate limiting and backoff; idempotent upserts; normalization adapter; monitoring of lag and failures.
